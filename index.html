Pathlight.ai

An AI-powered resume tailoring tool — my deepest exploration of LLM orchestration, async Python, and prompt engineering for a practical job-search use case.

// The Problem

Tailoring a resume for each job description is tedious, error-prone, and difficult to scale manually. ATS systems filter out applications where keywords don't match the JD — even for qualified candidates. I wanted to build a system that could automate this process intelligently.

// Goal & Scope

Build a personal tool that accepts a job URL and a base resume, scrapes the job description, and uses an LLM to produce a tailored, ATS-optimized version. My primary learning goals were async task architecture and LLM workflow orchestration.

// What I Built

A FastAPI backend that accepts resume and job URL, uses Apify to scrape the job description, and sends both through a LangGraph-orchestrated prompt chain to Gemini. Celery and Redis handle the async queue so the API never blocks. WeasyPrint renders the final output to PDF.

// Key Challenge

My first version was synchronous — the endpoint waited for the entire LLM response before replying. Under any real load, this timed out. Introducing Celery queues was the right fix, and it taught me why async task architecture matters in LLM applications where inference is slow.

// Prompt Engineering

Getting the LLM to rewrite only relevant sections without hallucinating fake experience took significant prompt iteration. I learned to use structured output formats (JSON intermediates) to constrain what the model was allowed to change — a technique I now apply to all my LLM work.

// What I Learned

Async architecture is not optional for LLM apps. Prompt engineering is an iterative engineering practice, not a one-shot task. LangGraph made complex multi-step workflows significantly easier to reason about and debug compared to a plain chain.

# Celery worker handles the slow LLM call asynchronously
@celery_app.task(bind=True, max_retries=3, acks_late=True)
def tailor_resume(self, task_id: str, payload: dict):
    try:
        # LangGraph chain: parse JD → rewrite sections → validate output
        result = tailoring_graph.invoke({
            "resume": payload["resume"],
            "job_description": payload["jd"]
        })
        pdf_path = render_pdf(result["html"])
        redis.set(task_id, {"status": "done", "url": pdf_path})
    except Exception as exc:
        # Retry with exponential backoff on transient failures
        raise self.retry(exc=exc, countdown=2 ** self.request.retries)

PulseOps AI

An exploration of multi-agent coordination for IT incident triage — built to understand agentic patterns, local inference, and retrieval-augmented generation in an enterprise operations context.

// The Problem I Explored

SRE teams deal with alert fatigue — many alerts, manual classification, and slow escalation paths. I wanted to understand whether a multi-agent system could automate the first-pass triage and routing of IT incidents using local AI models.

// Architecture Approach

A chained pipeline where each agent has one responsibility: a Parser Agent extracts structured fields from alert text using Llama 3.2 (via Ollama), a Triage Agent scores severity, a RAG Agent searches historical incidents, and an Allocation Agent suggests the best-fit responder.

// Why Local Inference

I chose Ollama with Llama 3.2 rather than a cloud API for two reasons: I wanted to explore local inference constraints, and incident data is often sensitive. The trade-off is smaller context windows and reduced accuracy compared to GPT-4 — a trade-off I documented and accepted for this use case.

// RAG Implementation

Instead of FAISS, I built an in-memory TF-IDF engine using NumPy. This was intentional: SRE incident descriptions are keyword-dense (terms like "OOMKilled", "502 Bad Gateway" are highly specific), making sparse vector matching a reasonable fit. It also runs entirely on CPU with sub-millisecond latency.

// Honest Limitations

This is a personal project, not a production deployment. The knowledge base is a synthetic dataset. Llama 3.2's smaller parameter size limits reasoning depth. The design is meant to explore the pattern, not claim production readiness.

// What I Learned

Multi-agent coordination requires careful state management between steps. Local LLMs are viable for structured extraction tasks but need prompt engineering guardrails. Choosing sparse vs. dense retrieval is a domain-specific decision, not a universal answer.

Cardiac Anomaly Detection

University research project applying supervised ML to clinical data — resulted in a published patent. Taught me to think carefully about what the right evaluation metric is for a given problem domain.

// Research Goal

Explore whether standard supervised learning algorithms could improve early-stage cardiac disease detection using aggregated clinical data from multiple sources. Conducted as part of a research assistant role at SRM University.

// The Core Insight

My initial model optimized for Accuracy — and hit 93%. But the dataset was heavily imbalanced. Accuracy was the wrong metric. In clinical settings, a False Negative (missed disease) is far more costly than a False Positive. The real objective was Recall (Sensitivity).

// Technical Approach

Applied SMOTE to address class imbalance during training. Used a custom cost-sensitive loss matrix in XGBoost to penalize False Negatives more heavily. Dropped the decision threshold from 0.5 to 0.35 to further improve Recall at the cost of Precision — a clinically acceptable trade-off.

// What I Learned

Model evaluation must be grounded in the domain. Standard metrics are starting points, not conclusions. The same principle applies in AI systems — evaluating an LLM on a generic benchmark doesn't tell you if it's right for your specific use case. Domain-constrained evaluation is a discipline I now carry into all my AI work.

evaluation.py — domain-constrained evaluation gate Python 
def evaluate_for_clinical_domain(y_true, y_pred_proba, threshold=0.35):
    # Lower threshold: accept more false positives to catch more true positives
    y_pred = (y_pred_proba >= threshold).astype(int)
    tn, fp, fn, tp = confusion_matrix(y_true, y_pred).ravel()

    recall = recall_score(y_true, y_pred)
    # In this domain, a high false-negative rate is unacceptable
    if fn > tp * 0.05:
        raise ValueError(f"FN rate too high for clinical use: {fn}/{tp}")

    return {"recall": recall, "false_negatives": fn, "false_positives": fp}

WhatsApp Booking Automation

A practical automation project — connecting WhatsApp to Google Calendar through n8n to handle appointment booking without any human in the loop for standard cases.

// The Problem

A small business was spending several hours per week manually reading WhatsApp messages and creating Calendar events. Every time a new booking scenario appeared (cancellation, reschedule), it required developer intervention in a monolithic Node.js handler.

// What I Changed

Moved the intent routing logic from hardcoded regex in Node.js into n8n's visual workflow editor. Node.js retained only the webhook signature verification. New booking scenarios are now added as n8n nodes — no code deployment required.

// Trade-off I Made

n8n introduces an extra network hop (~50ms). For a booking confirmation bot with natural human response expectations, this is imperceptible. If this were a real-time trading API, the choice would be different. Latency tolerance is context-dependent.

// Outcome

Standard booking flows (check availability, confirm slot, send confirmation) run fully automatically. Estimated 70% reduction in manual scheduling effort for the use case. New intent types are deployable in minutes, not hours.

// Approach

How I Build AI Systems

Principles I try to apply — not claims of mastery, but the considerations I bring to every AI system I design.

⚡
Async by Default
LLM calls are slow. Any endpoint that waits synchronously for inference will time out under any meaningful load. Queues first, results later.
🔁
Retries & Fallbacks
External APIs — especially LLM APIs — fail. Every call gets a timeout, retry policy, and ideally a fallback path. Graceful degradation is better than hard failure.
📐
Structured Outputs
Free-text LLM responses cannot be trusted to have consistent format. I use Pydantic models and structured prompting to constrain what the model returns.
🧪
Evaluation First
Changing a prompt without an eval dataset is guesswork. I build ground-truth test cases before iterating — even if they're small — so I can measure whether changes help or regress.
🔍
Context Engineering
The quality of context you give an LLM determines the quality of output. Retrieval, chunking strategy, and prompt construction are engineering problems, not afterthoughts.
📡
Observability
If a workflow fails silently, you can't fix it. I instrument LLM calls with traces, token counts, and latency metrics so failures are visible and debuggable.
💰
Cost Awareness
LLM inference costs real money. Prompt design, model selection, and output caching all affect cost. I keep token usage in mind during design, not as an afterthought.
🧩
Modular Design
Systems where every component can be tested and replaced independently are far easier to iterate on. I try to keep agents, retrievers, and LLM calls as separate, swappable units.
👤
Human Review Paths
AI systems make mistakes. Especially in early versions. Any workflow with meaningful consequences should have a path for human review on low-confidence cases.
🔒
Prompt Injection Awareness
User input going directly into prompts is a security surface. I treat user-supplied strings as untrusted and sanitize or constrain them before including them in LLM context.
📚
Reading the Code, Not Just the Docs
When something doesn't behave as expected in LangGraph or FastAPI, I read the source. Understanding what a framework actually does prevents magical thinking.
🌱
Continuous Learning
AI tooling evolves extremely fast. I follow research, experiment with new frameworks, and rebuild things I've already built to understand what improved and why.

// Engineering Decisions

Why I Chose What I Chose

The decisions I made in my projects, the alternatives I considered, and the trade-offs I accepted.

LangGraph over a plain LangChain chain
→ Chose: LangGraph
Reason
LangGraph models workflows as a graph with typed state. This makes multi-step flows with conditional branches and retries far easier to reason about and debug.
Alternative
LangChain LCEL chains: simpler, but linear. Hard to implement conditional re-routing or memory between steps without significant boilerplate.
Trade-off: steeper learning curve, more setup
Celery + Redis over asyncio background tasks
→ Chose: Celery + Redis
Reason
Tasks survive process restarts. Workers are monitorable via Flower. Retries are built-in. In-process background tasks would lose all queued jobs on a crash.
Alternative
FastAPI BackgroundTasks: zero setup, but in-memory — all queued work is lost if the process dies. Not appropriate when each task represents user data.
Trade-off: operational overhead worth it at any real scale
TF-IDF over dense embeddings (PulseOps RAG)
→ Chose: TF-IDF (sparse)
Reason
Incident descriptions are keyword-dense. Terms like "OOMKilled" and "502 Bad Gateway" are highly specific. Sparse vectors weight rare, exact terms heavily — which is exactly right for this domain.
Alternative
FAISS + sentence-transformers: better semantic recall, but requires GPU or significant CPU overhead. Overkill for a personal project, and semantically less precise here.
Trade-off: lower semantic recall — acceptable for this domain
n8n for workflow routing over more Node.js
→ Chose: n8n orchestration
Reason
New intents can be added as visual nodes in n8n without a code deployment. Non-technical collaborators can understand and edit the flow. Decouples business logic from code.
Alternative
Expanding the Node.js handler: tighter coupling, every new intent requires a code change + deployment. Gets messy fast as the number of intents grows.
Trade-off: ~50ms extra latency — imperceptible in this context
Recall over Accuracy as the primary metric
→ Chose: domain-constrained loss function
Reason
In clinical ML, a False Negative (missed disease) is categorically worse than a False Positive (unnecessary test). Accuracy hides this on imbalanced datasets. Recall was the correct objective.
Alternative
Standard Accuracy / F1: maximizes overall performance but gives the dataset's majority class (healthy) undue influence. A model saying "healthy" for everyone scores 93% accuracy.
Trade-off: precision -6%, recall +25% — correct for this domain, led to patent
FastAPI over Flask for all backends
→ Chose: FastAPI
Reason
Native async support, Pydantic validation baked in, automatic OpenAPI docs. These aren't luxuries in LLM applications — async and schema validation are requirements.
Alternative
Flask: simpler API, large ecosystem, but synchronous by default. Adding proper async and request validation requires multiple extensions and more boilerplate.
Trade-off: slightly steeper initial setup
