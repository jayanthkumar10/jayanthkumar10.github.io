AI Clinic Receptionist

A highly robust, stateful conversational agent serving as a medical clinic receptionist on WhatsApp. Built on n8n using a scalable Hub-and-Spoke pattern with Redis for global state management and transactional locks.

n8n Redis Gemini 2.5 Flash Google Sheets
Private Repository

The Problem

A medical clinic was spending hours manually parsing incoming WhatsApp messages and creating Calendar events. Furthermore, building stateless LLM chatbots is easy, but building a stateful, transactional booking system on top of stateless webhooks (WhatsApp/Telegram) requires severe guardrails against race conditions, duplicate bookings, and conversational hallucination.

Hub-and-Spoke Architecture

Engineering Decisions

Redis State Management over Stateless Prompts

The Alternative

Passing the entire conversation history into the LLM prompt every time and asking it to deduce the current step (e.g., "Are we picking a doctor or a date?").

The Decision

I implemented an external state machine in Redis. It explicitly tracks the user's current step (MENU, AWAITING_DOCTOR, AWAITING_SLOT_CONFIRM). This drastically reduces LLM hallucination and allows deterministic routing to the correct sub-workflow.

Trade-off: Requires managing cache invalidation, timeout handling (e.g., automatically resetting stuck sessions after 30 minutes), and self-healing logic if the Redis instance wipes.

Transactional Slot Locking

The Alternative

Assume that if a user says "I want 9:00 AM", the slot is definitely free, and immediately call the Google Calendar API.

The Decision

In a high-traffic clinic, two patients might request 9:00 AM simultaneously. The Spoke Workflow implements a strict Concurrency Check. It appends a PENDING row to Google Sheets to establish an atomic lock. Only after the lock is verified does it create the Calendar Event and upgrade to BOOKED.

LLM Fallback Extraction

The Alternative

Expect the LLM to return perfect JSON 100% of the time, and crash the webhook if it wraps the JSON in markdown (```json ... ```).

The Decision

I built a 3-layer safety net in a Custom Code node. It first strips markdown. If `JSON.parse` fails, it falls back to a Regex extractor. If that fails, it defaults to a safe `UNKNOWN` intent, preventing total system crashes.

Session Auto-Recovery via Chat ID

The Alternative

If the Redis session is lost due to cache eviction, ask the user to completely restart the booking process from scratch.

The Decision

The webhook intercepts all messages and queries the Google Sheet using the sender's Phone Number. If it finds a PENDING booking for that ID, it automatically restores the Redis state to the exact step the user left off on, without them even realizing the cache was dumped.

Trade-off: Requires an additional read query to Google Sheets on the first message of a potentially dead session, slightly increasing latency on cache misses.

The Outcome

The system successfully acts as a highly empathetic, natural-language receptionist while enforcing strict enterprise rules on the backend. It handles third-party bookings (booking for a child), auto-recovers from lost state by scanning the database via Chat ID, and intelligently routes standard FAQs to a local knowledge base to bypass LLM latency entirely.
