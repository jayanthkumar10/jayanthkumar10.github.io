AI Clinic Receptionist

A highly robust, transactional conversational assistant serving as an automated receptionist. Orchestrated on n8n using a scalable Hub-and-Spoke pattern with Redis session caching and atomic calendar slot locks.

The Problem

A high-traffic medical clinic spent over 15 hours weekly answering repetitive scheduling messages. While stateless LLM bots are simple to spin up, building a transactional, stateful booking agent on top of stateless message webhooks (WhatsApp/Telegram) introduces major engineering challenges.

The system must manage concurrent slot requests (preventing two patients from booking the same 9:00 AM slot), withstand mid-conversation session drops, extract complex structured variables (dates, names) from unstructured conversations, and remain resilient against rate limits or server errors.

Core Engineering Decisions

Redis State Management vs Stateless Prompts

The Alternative

Feed the entire messaging logs history into the LLM on every incoming webhook and ask the model to guess the current booking stage.

The Decision

Relying on LLM memory is slow and prone to hallucination. I designed an external finite state machine (FSM) inside Redis. Redis explicitly tracks the user's current step (e.g., MENU, AWAITING_SLOT, AWAITING_CONFIRMATION). This limits the LLM's role to extracting target parameters, stabilizing the flow.

Trade-off: Requires managing cache invalidation and auto-expiring inactive session tokens after 30 minutes, but guarantees reliable slot transitions.

Optimistic Slot Locking

The Alternative

Query availability and immediately insert calendar slots without checks, causing double bookings if multiple users click concurrently.

The Decision

Implemented transactional concurrency locks. Before confirming a booking, the sub-workflow writes a temporary PENDING slot status in Google Sheets and checks the row state. If another booking process updated the slot first, the agent detects the conflict, releases the lock, and prompts the user to select another slot.

Three-Layer Parse Safety Net

The Alternative

Crash the webhook or ignore the message if the LLM output deviates from the expected JSON format.

The Decision

LLM JSON blocks occasionally contain markdown formats or trailing commas. I built a 3-layer parsing wrapper in a Custom JS node: it first sanitizes markdown wrappers, falls back to a regex parser on failure, and defaults to a safe UNKNOWN intent if extraction completely fails, preventing webhook crashes.

State Recovery via Phone Matching

The Alternative

If the Redis session expires or is flushed, require the user to restart the booking from step one.

The Decision

On cache misses, the orchestrator queries Google Sheets by phone number. If it discovers a active PENDING reservation row, it restores the session variables back to Redis, allowing the user to seamlessly resume their chat.

Trade-off: Adds a query check on cache misses, but creates a frictionless user experience.

Operational Outcome

The clinic booking agent automates the scheduling pipeline, allowing natural conversational interactions while enforcing deterministic backend constraints. It manages scheduling, rescheduling, cancellations, and frequently asked questions securely, drastically reducing support staff workload.
